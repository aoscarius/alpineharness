# Isolated Project Workspace Wrapper (Sandbox)

A lightweight, automated infrastructure based on **Docker** and **Make** designed to instantiate isolated development workspaces directly inside your project directories.

This tool generates a global CLI wrapper (`pi`, `omp`, or `opencode`) that launches a ephemeral container in the background. The container dynamically maps your host user and group IDs, securely mounts your current working directory, and isolates project-specific dependencies or API keys within a dedicated local hidden directory.

## Key Features

* **Workspace Isolation:** Automatically provisions a local hidden directory (`.<harness>/`) and a `.env` file to separate configurations for every project.
* **Permission Persistence:** Dynamically creates the sandbox user inside the container matching your host UID/GID, permanently preventing `root` file ownership issues on your host system.
* **Secure Shared Assets (Optional):** Supports read-only mounting of your host SSH keys (`~/.ssh`) and global Git configuration (`~/.gitconfig`).
* **Resource Constraints:** Enforces strict hardware limits on container execution (CPU and Memory) via a central configuration file.
* **Advanced Shell Prompt:** Features a pre-configured interactive Bash shell equipped with colorized aliases and a visual indicator for the active Git branch.

## Installation & Commands

### Prerequisites
Ensure that `make` and `docker` are installed and running on your host machine. Additionally, verify that `~/.local/bin` is included in your shell configuration file (e.g., `.bashrc` or `.zshrc`) within your system's `$PATH` variable.

### 1. Initial Configuration
Before installing, you can optionally customize hardware limits or provide default build variables by creating a `docker.env` file in the same directory as the Makefile:
```env
DOCKER_MAX_MEMORY=4g
DOCKER_MAX_CPUS=2
OPENROUTER_API_KEY=your_token_here
```

### 2. Management Commands (Makefile)

The `Makefile` exposes the following core operations:

| Command | Description |
| :--- | :--- |
| `make build` | Builds the Docker image locally for the selected harness. |
| `make install` | Builds the image and deploys the global Bash wrapper script to `~/.local/bin`. |
| `make uninstall` | Completely purges the global wrapper script, templates, and shared assets. |
| `make help` | Displays the help menu with all available commands and default flags. |

> 💡 **Note:** The installation defaults to the `pi` harness. You can target alternative harnesses (such as `omp` or `opencode`) by passing the `HARNESS` variable to the command line:
> ```bash
> make install HARNESS=omp
> ```

## Usage Guide

Once installed, you can invoke the wrapper globally using the configured harness name (e.g., `pi`) from **any project directory on your computer**.

### Launch an Isolated Interactive Shell
To spin up a container and drop into an interactive development session:
```bash
pi --shell
```

### Execute Commands Directly via the Harness
If you omit the `--shell` flag, the wrapper automatically forwards all arguments directly to the global harness executable inside the container:
```bash
pi run agent --task "Initialize an Express server"
```

### How Workspace Initialization Works
When executed inside a workspace directory for the first time, the wrapper automatically handles environment setup:
1. It creates a local hidden directory `.<harness>/` (e.g., `.pi/`).
2. It provisions a project-specific local `.env` file copied from your shared templates.
3. **Automatic Git Integration:** If the workspace is a Git repository, the script automatically appends both the `.env` file and the `.<harness>/` directory to your `.gitignore` to prevent committing local caches or credentials.

---

## Deployed File Structure

Upon successful installation, system files are laid out across the following host directories:

* **`~/.local/bin/<harness>`**: The autogenerated global Bash wrapper script that intercepts commands and configures Docker runtime flags.
* **`~/.local/share/<harness>/.env`**: The central environment template used to populate initial variables for new workspaces.

---

## Security & Privileges

* Containers are executed with the `--rm` flag, ensuring the container state is fully purged upon exiting the shell. Your code remains safe on your host file system via secure Docker volume bindings.
* The internal `sandbox` user belongs to the `wheel` group and is pre-authorized for passwordless `sudo` access, allowing you to install temporary packages at runtime (`apk add`) if needed.
